## U1.1 + U1.2 — /agents 首屏：先给结论，再给主动作（可读）

**为什么**
走查 dashboard / inbox / agents 三页首屏后，三问覆盖率如下：dashboard 三问都有答案但需二次解读（同屏两个「需要我」的数字口径不明，`DashboardPage.tsx#L371` 与 `#L410-L413`）；inbox 第三问答不上（「自动处理」tab 无计数徽标，`InboxPage.tsx#L2042-L2045`）；agents 三问有两问答不上——
- 页头唯一动作是向后的「返回自动化配置」，真正的前进动作「批量开通」埋在搜索行（改前 `AgentListPage.tsx#L339-L343`、`#L413-L417`）；
- 首屏四张卡是目录统计而非结论，且「可开通 11」把 7 个可开通与 4 个需升级套餐混算（改前 `#L370-L376`），人要自己拆；
- 「为什么有的 Agent 还没开」只出现在表格行内红字依赖（`getMissingDeps`，`#L132-L135`）。

按「少解读一次 / 少点一次」排序，agents 缺口最大，故本轮落在 /agents。完整缺口清单见 `ui-roadmap.md` 的 U1.1 表。

**改了什么**（/agents 首屏）
1. 标题下新增一条结论条（13px，左蓝边，浅底）：「已开通 4/15 个 Agent，正在处理 4 个任务；7 个现在就能开通。」副句直接给出「另有 4 个需要升级套餐 · 其中 1 个依赖尚未开通的前置 Agent，开通时会按依赖顺序一并打开」。三句分别回答「现在什么情况 / 我该做什么 / 系统会怎么配合」，且第一句的数字能和 15 对上账（4+7+4）。
2. 页头主动作改为「开通这 7 个 Agent」（primary），数量与结论条同源；「返回自动化配置」降为默认按钮并换设置图标，不再站在主动作位置。
3. 搜索行右侧重复的「批量启用…（7）」按钮移除 —— 同一动作全站只留页头一处。

**强化了哪一层**：可读（结论前置 + 口径写在数字旁边）。附带的可行收益：主动作从搜索行移到页头，Tab 少走约 8 站。

**边界与取舍**
- 保留四张指标卡：它们是结论的支撑证据，不是重复结论；只把结论提到它们之前，不删信息。
- 不动数据、不动接口、不改开通语义；结论条里的三个数字全部来自页面已有的 `enabledList` / `agents` / `totalActiveTasks` / `disabledAgents` / `getMissingDeps`，可回溯。
- 「可开通 11」这张卡（含 4 个需升级）本轮不改写口径，由结论条的「另有 4 个需要升级套餐」承接解释；卡片自身口径记入后续可读性候选（未立项）。
- 本轮同时勾掉 U1.1（走查清单）与 U1.2（落地）：纯审计轮没有用户可感知变化，答不上「改错了人能在界面哪里看出来」，故同轮闭环审计选出的第一缺口。
- 未新增依赖、未新增页面/模块；新增 CSS 仅一个类 `.agent-conclusion`，颜色全部 token（`--ark-panel-soft` / `--ark-ink` / `--ark-blue` / `--ark-muted`），亮/暗各有一套值。

**验证**
- `npm run build`：通过（tsc + vite，9s 级；仅既有 chunk>900kB 警告）。
- `scripts/check-hex.sh`：360 行裸 hex，与本轮前基线一致 —— 本轮改动零新增裸 hex。
- 浏览器（dev server 实测，960×632 视口）：亮色结论条 `rgb(248,250,252)` 底 / `rgb(23,32,51)` 字；深色 `rgb(22,32,51)` 底 / `rgb(229,238,252)` 字，对比约 13.9:1；切回亮色与初始一致。
- 键盘：Tab 顺序「…退出演示 → 返回自动化配置 → 开通这 7 个 Agent」，主按钮可达且有可见焦点环（截图 btn-focused-dark-2.png）。
- 宽度：环境视口固定 960，无法取 1440/1024 实测；以 960（窄于 1024）为最坏态验证结论条可换行、页头两按钮不溢出。1440 下的单行效果未实测，记为本轮验证残留。
- 走查副产物：硬刷新后 `data-theme` 首帧回落为 light（localStorage 已存 dark），主题选择器仍显示深色 —— 可信层既有缺陷，记入候选（属 U4.3 归口），本轮不修。

**三问自检**
- 少解读了什么：不用再自己去「15 减 4」算差额，也不用点开批量抽屉才知道为什么有几个开不了。
- 少点了几下：开通动作从「找到搜索行右侧按钮」变成页头主按钮，且不再需要先切到批量抽屉去数候选。
- 改错了怎么看出来并撤回：结论条就在标题下，数字与「已开通」卡、「可开通」卡、页头按钮三处交叉可对；错了改文案或删掉这一条即可还原，开通动作仍走原有二次确认抽屉，可取消。

## U1.3 — /inbox 首屏补第三问：系统自动处理条数前置（可读）

**为什么**
走查证据 I1：inbox 首屏三个 tab 里，「待处理」带红色计数徽标（`InboxPage.tsx#L1622`），而「自动处理」没有（改前 `#L2042-L2045`），所以「系统替我做了什么」必须点进第三个 tab 才知道。三问里的第三问在首屏无答案。

**改了什么**
1. 「自动处理」tab 标签右侧新增计数徽标：近 7 天系统自动处理的条数（实测 9），首屏不用切 tab 就能读到「自动处理 9」。
2. 数字口径与 tab 内容同源：`InboxAutoHandledTab.tsx` 的筛选逻辑提取为 `getAutoHandledRows()`，徽标计数、表格行数、tab 内汇总卡「自动完成 N 项」三处共用，不会各算一套。
3. 徽标语义与「待处理」区分：待处理是红色实心（要人动），自动处理是中性描边（只报数、不催促）；悬停 title 写明「近 7 天 … 项」。

**强化了哪一层**：可读（结论前置 + 口径与时间写在数字旁）。不影响操作路径。

**边界与取舍**
- 「自动处理」按账户级口径统计（治理回执跨店，tab 内容本身也是账户级），不随页头店铺范围收窄；并列的「待处理」徽标则随范围变化。两者口径不同，故用颜色与 title 的「近 7 天」显式区分，不做统一。
- 不改审计日志的筛选口径（P41.1 已定「谁算 Agent / 谁算回执」），本轮只复用。
- 首版徽标用 `--ark-border-soft` 填充，浏览器实测与页签条底色对比仅 1.05:1，胶囊形状不可见；改为「`--ark-panel` 底 + `--ark-muted` 字 + 同色 1px 内描边」，形状成立。
- 未新增依赖、未新增后端、未造只展示的假入口；用户可见文案新增 1 条 i18n key（中英各一份）。

**验证**
- `npm run build`：通过（tsc + vite，12s；仅既有 chunk>900kB 警告）。
- `scripts/check-hex.sh`：360 行裸 hex，与基线一致，本轮零新增；新增颜色全部 `var(--ark-*)`。
- 浏览器（真实登录 merchant@allmall.cn）：亮色徽标 9 = tab 内表格 9 行 = 汇总卡「自动完成 9 项」；深色同为 9。亮色徽标底 `rgb(255,255,255)` / 字 `rgb(91,107,132)`（5.41:1）/ 描边对页签条底 `rgb(245,247,251)` 5.04:1；深色 `rgb(17,24,39)` / `rgb(148,163,184)`（6.92:1）/ 描边对 `rgb(11,17,32)` 7.34:1，两套主题下胶囊轮廓与数字都清晰。
- 宽度：环境视口固定 960（窄于 1024），三个 tab 单行、`scrollWidth = clientWidth`、无横向滚动与裁切；1440/1024 无 resize 能力，未逐像素实测，以 960 为最坏态，记为本轮验证残留（720px 以上无宽度断点）。
- 键盘：未单独实测本轮徽标；tab 为 antd 原生可聚焦控件，未改动焦点顺序。

**走查副产物（本轮不修，已归口）**
- 深色下选中 tab 文字 `rgb(34,87,203)` 对页面底 `rgb(11,17,32)` 仅 2.95:1，读起来发暗 —— antd 选中色未随主题走，属可信层，已作为证据写入 `ui-roadmap.md` 的 U4.3。
- 侧边栏「待办中心」徽标显示 27，而待处理 16 + 自动处理 9 = 25，差 2；侧边栏走 dashboard summary、与 tab 口径不同源，记为后续候选，不做。

**三问自检**
- 少解读了什么：不用切 tab、也不用自己加总，就能说出「系统这几天替我处理了 9 件」。
- 少点了几下：少一次点击（原本要先点「自动处理」才看到条数）。
- 改错了怎么看出来并撤回：徽标数字与 tab 内表格行数、汇总卡三处交叉可对，错了删掉这段 Badge 即恢复原样，不影响数据处理逻辑。

## U2.1 — 核心页三态审计 + dashboard 首屏加载/失败态落地（可行）

**为什么**
U2.1 要求审计核心页「加载 / 空 / 错误」三态。审计结果（清单已写入 `ui-roadmap.md#U2.1`）：`PageSkeleton` 与 `EmptyState` 此前只服务路由懒加载与无数据，五个核心页没有一处用它处理数据加载或失败。其中 dashboard 最伤命题——首屏在数据没回来时就替人下结论：`storeCount=0` 触发「没有店铺 → 去体验演示」横幅（`DashboardPage.tsx#L394`），运营台写「全部清空」（`#L457`），关注清单也写「全部清空」，GMV 等卡片显示 0。落地页把「正在读取」读成「这家店没生意」，正是「界面替人做判断」的反例。

**改了什么**（只改 dashboard 首屏三态）
1. 加载态：`stores` / 经营指标 / 运营摘要三路查询任一在首次读取时，整页复用既有 `DashboardSkeleton`（`DashboardPage.tsx#L339-L342`），不再渲染任何结论句或 0 值。
2. 错误态：三路任一失败时，页面显示「经营数据没读出来，这不代表没有数据。重试一次，或稍后再看。」+「重新读取」按钮，就地重新拉取三路查询（`#L344-L362`），不再退化为 0 / 「没有店铺」。
3. 空态保持原样：onboarding 仍走 `StoreConnectionEmptyState`；真正 0 店铺的账号仍看到演示入口（数据到位后才出现）。
4. 新增 2 条 i18n key（中英各一份）：`dashboardv2.loadFailed`、`dashboardv2.loadRetry`；复用现有 `EmptyState` 与 `DashboardSkeleton`，无新组件、无新依赖、无新颜色。

**强化了哪一层**：可行（三态齐全 + 失败后一步可重试）。附带可读收益：加载期间不再出现「¥0 / 全部清空」。

**边界与取舍**
- 切换时间范围（当日 / 7 日 / 30 天）会短暂进入骨架而非保留旧数字：旧数字配新口径本身就是误读，宁可 180ms 空白也不显示错口径。这是本轮有意取舍。
- 只处理 dashboard：inbox / agents / orders / settings 的同类缺口已按严重度列进 U2.1 清单，留作后续候选，避免单轮超过最小可验证范围。
- 错误态用现有 `EmptyState` 而非新组件；文案明确区分「没读出来」与「没有数据」，避免二次误读。
- 未改任何数据、接口或业务语义；error/loading 分支都在查询层之上，删掉即回滚。
- 验证用过的两处临时改动（`client.ts` mockDelay 调 1800ms、`stores.ts#list` 注入 reject）已全部还原，最终源码与构建即为正式版本。

**验证**
- `npm run build`：通过（tsc + vite，10.5s；仅既有 chunk>900kB 警告）。
- `scripts/check-hex.sh`：360 行裸 hex，与基线一致，本轮零新增。
- 加载态（浏览器实测，临时把 mockDelay 调到 1800ms）：刷新 /dashboard 后 1.4s / 2.4s / 3.4s 三个采样点均为 22 个 `ant-skeleton` 节点、无 GMV、h1-h3 无文字；「没有店铺」「去体验演示」「暂无需要你处理的事项」检测均为 false；约 4.5s 后骨架清零，出现「经营总览」与 GMV ¥209,596、待处理 27 等真实数字。验证后还原延迟。

## U2.2 — /inbox 批量动作：确认写明后果，忽略可一键恢复（可行）

**为什么**
批量入口是全站唯一能一次改动十几条数据的地方，改前两个确认框只重复按钮名（「批量完成」「批量忽略」）：不说会有几条、不说会去哪、也不说能不能找回。一旦确认，十几条异常直接从待处理消失，唯一回退路径是切到「处理记录」逐条找「恢复」（批量完成连恢复都没有）。判断风险的责任被推回给人，正是「界面替人做判断」的反例。证据：改前 `InboxPage.tsx#L1673-L1692`（改动前行号）两个 `Popconfirm` 的 `title` 就是按钮文案，无条数、无后果；`exceptionsApi` 只有 `unignore`，没有恢复已解决的入口（`api/exceptions.ts#L434-L444`）。

**改了什么**
1. 两个确认框改为「完成这 N 项？/ 忽略这 N 项？」+ 一句后果：完成 → 移入处理记录并记下处理人与时间；忽略 → 从待处理移除、保留在处理记录、可随时恢复（`InboxPage.tsx#L1697-L1718`）。
2. 批量忽略的成功回执从纯文本变成「已忽略 N 项 + 恢复」，8 秒内点「恢复」即把这批条目一次性放回待处理，随后回执「已恢复 N 项到待处理」（`#L718-L748`）。
3. 恢复复用历史页逐条恢复的同一个 API（`exceptionsApi.unignore`，含审计），口径一致；无新接口、无新依赖、无新颜色，文案中英各 5 条。

**强化了哪一层**：可行（危险动作先讲后果 + 忽略可撤回 + 每步有回执）。附带可读收益：条数直接写在确认框标题里。

**边界与取舍**
- 只把「忽略」做成可撤回。「完成」缺少 reopen 语义（异常只有 `unignore`），硬造会让「已完成」与「处理记录」互相矛盾；故完成保持一次性，用确认框写明「记录处理人与时间、之后仍可回看」，满足 U2.2 的「撤回或留痕」。若下轮要做完成撤回，需先按阶段规则在 `roadmap.md` 登记 P 项补 reopen 语义。
- 不做多级撤销栈，只保留最近一次忽略的一步撤回：够用，且不引入新的状态机。
- 恢复不重放忽略时已释放的 Agent 暂停与通知已读状态，这两项按既有语义落定；回执只说「回到待处理」，不承诺「完全复原」。
- 选中态不做恢复：实现过，浏览器实测复选框未回填，直接去掉，避免给出无法验证的承诺。

**验证**
- `npm run build`：通过（12.5s；仅既有 chunk>900kB 警告）。
- `scripts/check-hex.sh`：360 行，与基线一致，本轮零新增。

## U3.1 — 键盘焦点基线：看得见焦点，一个动作一次 Tab（可行）

**为什么**
U3.1 走查证据：`global.css` 全文没有任何 `:focus-visible` / `outline` 规则（改前 `grep focus-visible src` 零命中），所以纯链接（侧栏菜单外的 `Link`、dashboard 关注清单的行链接）键盘聚焦后完全没有指示；antd 组件的焦点环取派生的 `colorPrimaryBorder`=`#a3c9ff`，对白底只有 1.7:1，键盘走查时等于看不见。更糟的是 `a` 包 `button` 的写法让一个动作占两次 Tab 停靠，且第一次停在一个无可见焦点的锚点上：`RoleFocusCard.tsx#L152-L156`（放权与护栏）、`#L194-L198`（去处理 / 只看我的）、`#L248-L252`（待我审批 / 全部审批）、`DashboardPage.tsx#L461-L466`（去处理）。键盘用户要么以为自己没动，要么按两次才到按钮。

**改了什么**
1. 新增语义 token `--ark-focus-ring`（亮 `#1d4ed8` / 暗 `#93c5fd`，写在 `tokens.css`，两套主题各一份；对页面底分别约 6.6:1 / 9.9:1）。
2. `global.css` 增加全局焦点环基线：`a` / `area` / `summary` / 非 -1 的 `[tabindex]` 在 `:focus-visible` 时统一 2px 实线 + 2px 外扩。此前完全没有指示的链接现在有环，且不加尺寸、不影响鼠标点击（`:focus-visible` 只在键盘时生效）。
3. antd 焦点环改色：`providers.tsx` 显式设 `colorPrimaryBorder`（antd 的 `genFocusOutline` 就用它），亮色环从 `#a3c9ff` 变为 `#1d4ed8`，暗色为 `#93c5fd`；环宽仍是 antd 默认 3px，不动尺寸。
4. 一个动作只留一次 Tab 停靠：`RoleFocusCard` 的 5 个动作与 `DashboardPage` 的「去处理」从 `a > button` 改为按钮内 `navigate()`，外层锚点删除（`RoleFocusCard.tsx` 改用 `useNavigate`）。

**强化了哪一层**：可行（键盘可达 + 焦点始终可见，一个动作一次停靠）。

**边界与取舍**
- 只做焦点可见性与停靠次数，不动 Tab 顺序、不加跳转正文的 skip link、不引入 roving tabindex：本轮要的是「按 Tab 时永远知道自己在哪」，不是重排导航语义。
- 不加 `outline: 4px`/自定义动画，环宽沿用 antd 默认，避免视觉重量突然变大；只换颜色与来源。
- `colorPrimaryBorder` 同时是部分组件的主色描边来源，可能让个别 hover 描边略深一点：这是有意的取舍——与其为一个边缘 hover 效果保留看不见的焦点环，不如让键盘用户能看见位置；改动是单行 token，回滚即恢复。
- 只改了 dashboard 上的 `a > button`。/inbox 行内「查看详情」仍是 `a > button`（`InboxPage.tsx#L1271-L1273`），已有可见焦点环但仍是两次停靠，登记到 U3.2，不把本轮扩到第二页。
- 无新增依赖、无新增后端、无新 i18n key、无新增用户可见文案；新增颜色只有 tokens 里 2 个 token 与 providers 里对应的 2 个 antd 镜像值。

## U3.2 — 表单焦点环来源统一 + 表格动作一次 Tab（可行）

**为什么**
U3.1 留下的两笔账都在 U3.2 名下：
1. 页头「店铺范围」下拉键盘聚焦时，可见环仍是 antd 派生的 `controlOutline`（亮色实测 `rgba(5,122,255,0.06)`，白底几乎不可见；暗色 `rgba(53,115,248,0.22)`），和 U3.1 刚建立的「2px 实线 `--ark-focus-ring`」不是同一套语言 —— 同一个 Tab 走查里，链接的环看得见、表单的环看不见。
2. 全站仍有 4 处 `<Link><Button/></Link>`，一个动作占两次 Tab 停靠：`InboxPage.tsx#L1271-L1273`（审批「详情」）、`SetupConfigPage.tsx#L316-L318`（新增店铺）、`ProductManagementPage.tsx#L243-L245`（去收件箱）、`PortfolioGoalsCard.tsx#L748-L752`（跨店方案去收件箱）。U3.1 只收了 dashboard 上的 6 个动作，这 4 处漏网。

**改了什么**
1. `global.css` 新增一条表单焦点环规则：Select / Input / Textarea / InputNumber / DatePicker 聚焦时统一 `border-color` + `box-shadow: 0 0 0 2px var(--ark-focus-ring)`，形状与 U3.1 的链接环一致。排除 `status-error` / `status-warning`，校验失败的红环不被焦点环盖掉。
2. 4 处 `<Link><Button/></Link>` 改为按钮内 `navigate()`（`InboxPage`、`SetupConfigPage`、`SyncDigestCard`、`PortfolioGoalsCard` 各自取 `useNavigate`），一个动作一次 Tab 停靠；文字链接（表格里的商品名、审批标题）保持 `<Link>` 语义不变。
3. 无新增依赖、无新增后端、无新增 i18n key、无新增颜色；颜色只引用 `--ark-focus-ring`。

**强化了哪一层**：可行（键盘可达 + 焦点始终可见 + 一个动作一次停靠）。附带可信收益：表单与链接的焦点语言同源同色。

**边界与取舍**
- antd 的 CSS-in-JS 规则带哈希类名（特异性约 0,7,0）且注入在 global.css 之后，纯 `body` 前缀压不过（首版实测无效，环仍是 `rgba(5,122,255,0.06)`），故这两条声明用 `!important`，并在注释里写明原因。风险面被 `:not(status-error/warning)` 收窄。
- 没有改 antd token `controlOutline`：它同时供 Button 的 `primaryShadow` 使用，改成实心色会让所有主按钮多出一条深色底边 —— 一处 token 连坐全站，代价大于收益。
- 焦点环在鼠标点击聚焦时也会出现（antd 不区分 modality）：这是有意的取舍，同一控件只有一种聚焦表达，比「键盘能看见、鼠标看不见」的双标准更容易预测；`:focus-visible` 方案无法区分 Select 内部文本输入，故未采用。
- 未改动 Tab 顺序、未加 skip link、未改表格行内其它按钮；`<Link>` 文字链接保留原生语义（新标签打开、可复制地址）。

**验证**

- `scripts/check-hex.sh`：360 行裸 hex，与基线一致，本轮零新增。

## 附加任务（用户直接指派）— 6 页头部统计方块统一（可信）（2026-11-16）

**为什么**
1. 同一种「页头统计方块」在六页里有四套实现口径：促销活动是页面内自定义 `StatBox`（居中、标签 11px、值 20px，无图标位）；广告 / 库存 / 直播用 antd `<Statistic>`（标题 14px，值 20px 与 24px 混用，同一行卡片高度不等）；模型中心用 `MetricCard`（值 24px、gutter 16）；用量与账单是手写 `Card` + `MetricCard`（18px / 20px 混排）。

3. 1024 宽下更明显：`Statistic` 方案靠 flex 换行，5 块变 4+1 时末块被拉宽到 334px，与上面四块不等宽。

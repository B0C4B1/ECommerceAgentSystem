## V1.1 — 增长引擎：营销与库存

> **目标**：从"日常运营"升级到"主动增长"，覆盖商家的营销和库存决策场景。

### 新增交付
| 编号 | 模块 | 关键功能 |
|:--:|------|----------|
| V1.1-1 | **促销活动管理** | 活动创建（时间/店铺/折扣类型/预算）、活动日历（日/周/月视图）、活动效果看板（GMV/订单/ROI 环比）、优惠券模板管理 |
| V1.1-2 | **库存管理升级** | 补货建议（基于 7/14/30 天销量预测）、库间调拨建议、安全库存设置、库存周转率看板 |
| V1.1-3 | **广告投放可视化** | 广告账户总览（花费/展示/点击/转化）、分计划对比表、创意素材预览、ROI 趋势图 |

### 验收标准
- 促销：支持满减/折扣/秒杀三种活动类型，日历拖拽调整时间，活动期 vs 非活动期效果对比
- 库存：补货建议算力基于销量均值和安全库存公式，调拨建议显示源/目标库存差异
- 广告：4 维度 KPI 卡片（花费/ROI/CPC/转化率），分计划数据表格，广告 Agent 策略联动

## V1.5 — 自治治理：把「放权」做成可审计的闭环（P28–P31）

> **目标**：P1–P27 解决的是「界面承诺必须落到数据」；V1.5 解决的是「治理结构必须能收能放」。
> 判断标准不是又多了几个功能，而是三个问题能否被界面直接回答：
>
> 1. 人设的目标，Agent 是否给出可达性与代价？
> 2. 人划的护栏，是否只有一份、可预览、可追责？
> 3. 人处理的升级，是否有超时、有路由、能沉淀成规则？
>
> 状态：⏳ 未开始 | 规划日期：2026-11-13

### 新增交付

| 编号 | 主题 | 优先级 | 关键改动 |
|:--:|------|:--:|----------|
| P28 | **治理可信** | P0 | 护栏单一数据源、变更留痕与确认、调度真值、Agent 健康态 |
| P29 | **目标协商** | P1 | Agent 提议目标、节奏预测、账户级目标分配、护栏影响预演 |
| P30 | **升级退出机制** | P1 | Agent 主动请求决策、超时策略、决策沉淀为规则、影响排序、指派路由、人工接管 |
| P31 | **放权验收** | P2 | 复盘补成本与介入成本、放权建议、角色视角、复盘窗口对齐目标周期 |

#### P28 治理可信

**要解决的问题**：护栏在两处存储、两处展示、一处仲裁；改完不知道影响谁；运营台显示「自主运行中」，但离开页面就停。

**状态**：✅ 已完成

关键改动：

- [x] **护栏单一数据源**：`StoreGoal.constraints` 作为唯一可编辑源；`OperatingPolicy.guards` 改为派生只读；工作台、店铺详情、仲裁三处同源。
- [x] **护栏变更留痕**：记录 old → new、原因、操作者、时间；毛利下限、折扣上限、月预算等关键护栏变更需 Owner 确认并进审计。（工作台目标卡：变更前显示逐项 diff、原因必填、保存即写审计；卡片与审计页可回看记录）
- [x] **调度真值**：运营台区分「演示运行 / 真实调度」，显示上次巡检、下次巡检、调度器离线；不得默认显示「自主运行中」。（`getSchedulerStatus` 以巡检心跳为唯一依据；控制台标签为「演示运行 / 调度器离线 / 仅手动」，周期卡同步显示上次、下次巡检与巡检范围；离开工作台即登记停止）
- [x] **Agent 健康态**：授权失效、上游 Agent 未启用、连续空转让 → 显式阻塞状态与原因。（运营台「Agent 健康」行：按店铺授权、上游依赖、连续 3 天无执行三类归因；只报已启用 Agent，按根因聚合，附「去重连 / 去处理」直达入口）

验收标准：

- 修改毛利下限后，工作台、店铺详情与仲裁结果三处一致。
- 调度器停止时，运营台不再显示「自主运行中」，而是显示离线与上次巡检时间。
- 任一 Agent 阻塞时，工作台能定位到「哪个 Agent、卡在什么原因」。

#### P29 目标协商

**要解决的问题**：目标只能由人单向下达，Agent 不会还价；人看不到「按当前速度能不能达成、需要多少预算」。

**状态**：🟢 已完成

关键改动：

- [x] **Agent 提议目标**：基于近 30 天表现与预算，给出可达区间、所需预算、预计达成率与依据。（工作台「本店目标」卡 →「请 Agent 评估目标」；结论分偏低/可达/有缺口，展示近 30 天与上一周期、月至今与日均、月末预计、可达区间、增量预算与剩余预算；人一键采用后写回目标并按月至今校准进度，旧值→新值与依据进审计）
- [x] **节奏预测**：run-rate、预计达成日、落后预警；缺口超过阈值时主动升级。（目标卡按近 14 天日均推算月末 GMV、预计达成日与相对月末的天数；缺口 >10% 时 Agent 自动把「节奏升级」推进待办中心，同店同月一条，节奏恢复或跨月自动关闭，人无需先发现再登记）
- [x] **账户级目标**：账户目标 → 建议分配到店 → 人确认后写回单店目标，并保留分配依据。（多店铺概览顶部新增「账户目标」行：Agent 按各店月末预计之和给出建议账户目标，人只改一个总数；分配按近 30 天 GMV 占比拆分、尾差归占比最大的店，合计始终等于账户目标；确认后一次写回 N 家店目标，每家记录旧值→新值、权重与依据进审计，账户目标另留汇总；单店不显示该入口。）
- [x] **护栏影响预演**：调整护栏前展示过去 7 天的拦截条数与预计 GMV / 毛利变化。（调整目标弹窗内实时预演：过去 7 天按毛利/折扣/预算归因的拦截次数；按本轮已生成方案对比当前与新护栏，列出放开/多拦的动作品类与预计 GMV、毛利变化；毛利只按带预计毛利率的动作估算，无影响与未生成方案都有明确空态；判定口径与仲裁共用 `guardBlockKind`，预演只读不落库）

验收标准：

- 目标卡能回答「按当前速度能否达成、差多少、需要什么」。
- 调整护栏前先看到影响预演，而不是保存后才发现动作被拦。
- 账户目标可一键分配到店，分配结果与依据可追溯。

#### P30 升级退出机制

**要解决的问题**：升级只有「收件箱」，没有超时、没有路由、没有沉淀，人不处理就会静默堆积。

**状态**：✅ 已完成（P30.1–P30.6 全部收口，含 P30.5 通知与店铺维度路由残余）

关键改动：

- [x] **Agent 主动请求决策**：新增升级类型，带选项、默认建议与超时默认值。（P30.1：预算 / 毛利 / 折扣三类护栏冲突生成 `decision_request`，给出「维持护栏（建议）· 放行一次 · 先去改护栏」三选一，24 小时超时默认维持护栏，人可在收件箱内直接拍板）
- [x] **超时策略**：X 小时未处理 → 提醒 / 保守降级 / 暂停该 Agent / 上报 Owner，可按店铺配置。（P30.2：收件箱「升级超时策略」抽屉按店铺配置 1–168 小时与四种动作；提醒只累计次数、暂定只冻结该店该 Agent、上报只提升级别；保存后重算未结决策截止时间，人工决策自动解冻）
- [x] **决策沉淀**：重复同类升级支持「以后都这样」，生成护栏或规则；连续 N 次同类审批建议转为自动执行。（P30.3：同店同类型连续 2 次由人给出同一结论后，决策卡出现「以后都这样」；确认即生成店铺级决策规则，之后同类升级由 Agent 按规则收尾并记账，规则可在「升级超时策略」抽屉撤销；规则只写结论不代提交执行）
- [x] **影响排序**：按影响金额、目标缺口、风险排序，支持「今日 Top N」。（P30.4：升级项带可核对的金额影响——被拦动作的预计 GMV、目标缺口、预计成本；收件箱「按影响排序」把已量化项按金额降序排前，金额相同看风险级别，推不出金额的显示「影响未量化」排后；默认展示前 5 条并可展开全部，汇总行给出可量化条数与合计金额）
- [x] **指派与路由**：成员选择、通知、个人待办；按店铺 / 风险 / 金额路由。（P30.5：新增 `routeEscalation` / `routePendingEscalations`——已上报 Owner、可核对金额 ≥ ¥5,000、critical 路由给 Owner，决策请求路由给审批人，日常异常路由给运营负责人，路由依据写在条目上并留审计；收件箱新增「我负责的 (N)」队列，按成员名或角色命中；升级行显示「指派：成员（角色）」，绿标=Agent 路由、灰标=人工改派；指派弹窗改用成员表选项并预填 Agent 建议。通知与按店铺路由未做，见下条残余）
- [x] **指派通知与店铺维度路由**（P30.5 残余）：路由结果不只落在收件箱与审计，还要主动告诉被指派人；成员表要有店铺归属。（P30.5.b：成员表新增 `storeIds` 店铺归属，同角色多人时优先该店负责人，无归属才按角色兜底并在路由依据里写明「未指定负责人」；顶栏铃铛改为「指派给我的升级」面板，按成员名或角色推送未读通知，可逐条或一键标为已读，点通知直达待办中心；升级被解决 / 忽略后相关通知自动收口，改派时旧负责人通知作废。通知只做站内，不发邮件 / IM / 飞书，因为本地无真实发送端点，宁可不发也不显示「已发送」）
- [x] **人工接管**：Agent 级或店铺级暂停自动执行，保留提案。（P30.6：收件箱「升级超时策略」抽屉按店铺一键接管 / 解除；接管期间 Agent 仍诊断、出方案，但低风险自动提交被拦截，提案保留供人手动提交；接管人与时间写在条目上并留审计，店铺卡与经营周期卡同步显示橙色「人工接管」标签和说明。本轮只做店铺级，Agent 级沿用已有的超时暂停解冻）

验收标准：

- 一条升级能走完「产生 → 提醒 → 超时 → 升级 → 决策 → 沉淀」。
- 人不处理时不会静默堆积，而是按策略降级、暂停或上报。
- 同类升级第二次出现时，可直接套用上次决策或转为规则。

#### P31 放权验收

**要解决的问题**：复盘只看回写金额，看不到成本与人的介入成本，无法回答「该不该继续放权」。

## 自主推演机制（Autonomy Loop）

> **目的**：让迭代过程本身也符合产品命题——Agent 是执行主体，人只设目标、划护栏、处理升级。
> 机制落地为每小时定时任务：每轮自主选题、实现、验证、记录；人只验收摘要与升级项。

### 触发与节奏

- 每小时触发一轮（Asia/Shanghai）；也可随时手动触发，不必等整点。
- **单飞约束**：下一轮开始前先检查上一轮是否收尾；未收尾则先补齐记录，不并行开新轮。一轮超过一小时也不会重叠。
- **每轮推进一个闭环切片**，不跨 P 项。一个切片可以包含同一 P 项下的 2–3 个子项，条件是它们共享同一条数据链路、同一次构建、同一条走查路径；宁可一轮打通一个方向，也不要把一个闭环拆成五轮文案补丁。
- 取「顶部第一个仍有未勾选子项的 P 项」，把该闭环涉及的勾选项一次做完；闭环没打通时保留未勾选项并记录卡点，不谎报完成。
- P28–P31 全部完成后进入**自主推演**：不设终点，按 P32、P33……持续向下编号，每轮补一个最薄弱的治理闭环。
- **每 3 轮至少一次结构性轮**：新 P 项的首个切片必须落在跨模块或数据链路的断点上（如目标↔资源、护栏↔执行、决定↔规则），不允许连续 3 轮只改同一张卡片的文案、标签、按钮或空状态。

### 状态写法

- 子项完成即勾选；一个 P 项全部勾选后，把「状态」改为 ✅ 已完成；进行中改为 🔄 进行中。
- 每轮只允许改动与当前闭环直接相关的文件；上限 15 个（含文档）。真正的边界是「一次构建 + 一条走查路径能验证完」，不是文件数；超过 15 才拆轮。

### 每轮固定输入

`AGENTS.md` → `product-design.md` → `roadmap.md`（取顶部未完成项）→ `iteration-log.md` 最近三节 → 相关代码。

### 三道门（任一不过就停止并记录）

1. **目的门**：这一轮必须直接强化「设目标 / 划护栏 / 处理升级」之一，并在改动说明中写明强化了哪一个。
2. **数据门**：复用现有 domain 类型与 Mock API；界面上每个数字都能回溯到数据；不新增「看起来像」的假入口。
3. **验证门**：`npm run build` 通过；关键路径浏览器走查；不新增依赖除非无法复用；同步更新 `iteration-log.md` 与 `roadmap.md` 状态。

### 争议处理（不停止）

- 需要产品决策、新数据源或权限模型变更：先在内部按核心命题讨论——哪种方案让 Agent 承担更多判断、人决策更少、错了更容易被拦下；选最保守可逆的方案继续做，同时在 `notes/escalation-YYYY-MM-DD.md` 记下争议、选项与最终选择，供人回看。
- 构建失败：自行定位修复并重跑；两次修复无效则回滚本轮未验证改动，记录失败点，转向下一个子项，不停止。
- 单轮改动超过 15 个文件：按「读路径先通 / 写路径先通」拆成两轮，先落可验证的那一半，其余登记为下一轮，不停止。
- 同一区域连续 3 轮没有可感知收益：切换到另一个薄弱区域，不停止。
- 人不处理升级项时继续推进；升级项只累计，不作为阻塞。
- 循环没有终点，直到人主动暂停定时任务。

### 审计与人的位置

每轮在 `iteration-log.md` 追加一节（沿用 P 编号），只写：为什么、改了什么、规则口径、边界、验证。
人只做两件事：读每轮摘要、处理升级项；不参与过程。

### 每轮结束前的对齐检查

- 这轮让人少做了一次什么决策？
- 这轮让 Agent 多承担了什么判断？
- 这轮如果 Agent 判断错了，人能在哪里拦下？

三问有一问答不上来，本轮不算完成。

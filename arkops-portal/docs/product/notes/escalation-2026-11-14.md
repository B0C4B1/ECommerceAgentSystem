# 升级项：P30 内先做哪一项（2026-11-14）

## 争议

P30 还剩两个未勾选子项：

1. **P30.5 残余：指派通知与店铺维度路由**——需要站内信 / 邮件 / IM 推送渠道，以及成员表里的店铺归属。
2. **P30.6 人工接管**——店铺级或 Agent 级暂停自动执行，保留提案。

按「取顶部第一个仍有未勾选子项的 P 项」，两个子项同属 P30；先做哪个需要取舍。

## 选项

- **A. 先补通知与店铺路由**：要新增推送渠道依赖，或给成员表硬造「店铺归属」字段。当前没有真实推送服务，成员表也没有店铺关系数据，做出来只能是一个不落数据的假入口。
- **B. 先做人工接管**：只依赖已有的店铺、经营周期、自动执行配置与审计，能真实改变「Agent 是否自动提交」，不需要新数据源。
- **C. 两个都做**：超出单轮一个最小闭环的约束。

## 最终选择

选 **B**，理由：

- 符合核心命题：人一键接过执行权，Agent 继续产出方案但不自动执行；判断错了人随时解除，提案仍在。
- 最保守可逆：接管只是内存态开关 + 审计记录，解除即恢复；不改权限模型，不加依赖。
- A 依赖外部推送与新的成员-店铺关系，属于「需要新数据源/权限模型变更」，继续留在 roadmap，不先造假字段。

## 回看方式

- 接管入口：`/inbox` →「升级超时策略」→ 店铺卡「人工接管」。
- 生效位置：经营周期卡的「人工接管」标签与说明；低风险自动提交被拦截。
- 争议若需改判：解除接管即恢复自动执行，无数据迁移成本。

## 追加决策（同日 · P30.5 残余执行）

上一轮把 A 留在 roadmap，理由是「没有真实推送渠道与成员-店铺关系」。本轮必须推进该项，重新按核心命题判断：

- **选项 A1：接入飞书 / 钉钉 / Webhook 真实推送**。通知设置页只有通道配置与连通状态，本地没有发送端点与凭据；做出来会是「标记已发送、实际没发」的假链路，人反而更晚发现升级。否决。
- **选项 A2：只做站内指派通知 + 成员店铺归属**。成员表本身就是系统里的协作关系数据源，加 `storeIds` 不是伪造展示字段，而是 Agent 路由必须知道的事实；通知落在可核对的通知记录与铃铛面板上，已读状态落盘。可逆、无依赖、错了人能改。
- **选项 A3：两者都做**。超出单轮最小闭环，且 A1 无法诚实验证。否决。

**最终选择 A2**。补充口径：

- 通知只解决「哪条归我、为什么归我」，点击仍进入同一个待办中心，不新增第二套待办。
- 店铺归属只用于在「目标角色的候选人」里挑人，不改变金额 / 风险 / 护栏的路由判定，避免通知渠道反过来影响判断。
- 历史持久化数据缺 `storeIds`，恢复时按邮箱从种子补齐；种子成员新增的「拼多多店长」不会凭空塞进老账号，拼多多店的日常升级在老账号下仍按角色兜底，属于数据事实。

**回看方式**：顶栏铃铛「指派给我的升级」；收件箱条目上的路由依据括号里会写「XX 店负责人」或「未指定负责人，按角色兜底」。若要改判，改成员归属或人工改派即可，旧通知自动作废。

## 追加决策（同日 · P31.3 角色首屏）

**争议**：roadmap 写的是「Operator 首屏『升级』」，但代码里的升级路由只指向 Owner（高额 / 关键）、Approver（审批类）和 Admin（店铺日常），种子成员里也没有 Operator 角色。若按 roadmap 字面把 Operator 的「我负责的」队列搬上首屏，卡片会永远显示 0 条；若为了填满它给 Operator 硬造路由，又等于改治理规则来凑界面。

**选项**：

- **A. 新增 Operator 路由目标**：把店铺日常升级也派给 Operator。会改变既有「运营负责人」职责口径，且种子里没有 Operator 成员，属于为展示而改规则。否决。
- **B. 只给 Owner / Approver 做首屏，Operator 不做**：少一个角色，roadmap 验收不完整；且运营人员确实需要一屏看到日常升级。否决。
- **C. Admin 与 Operator 共用「运营队列」视角**：直接复用 `routeEscalation().role === 'Admin'` 的口径，卡片标题「升级」，标签显示当前角色（Admin / Operator），右上角注明与收件箱同口径。可逆、不新增数据、不伪造入口。

**最终选择 C**。补充口径：

- 卡片只聚合 Agent 已经判给运营的未解决升级，不新增「归谁」规则；Agent 改路由，首屏自动跟着变。
- 队列跨店铺，与收件箱一致；店铺过滤器只影响 Owner 目标卡。
- Finance / Viewer 不显示角色卡，避免造只读假入口。

**回看方式**：若将来成员表出现 Operator 且路由开始指派 Operator，只需把运营队列的过滤条件补上 `assigneeRole === 'Operator'`，卡片位置与跳转不变；若路线改为「Operator 只执行不处理升级」，删除该分支即可，无数据迁移成本。

## 追加决策（同日 · P33.1 目标节奏补救）

**争议**：节奏升级要变成可点选项，但「追加预算」到底要不要做成第三个选项？

**选项**：

- **A. 三个选项：维持 / 下调 / 追加预算**。追加预算需要改 `monthlyBudgetCap`，现有护栏写入要求「原因必填 + 影响预演」，收件箱里没有这两个字段；要么绕过护栏写入，要么再造一套预算表单。前者破坏 P28 的唯一数据源，后者是新入口。否决。
- **B. 两个选项：维持 / 下调至可达值**。两个结论都能用目标本身承接，写入路径就是既有 `saveGoal` 语义（改目标 + 校准进度 + 审计）；预算需求写在摘要里，人愿意加预算仍走目标卡原弹窗。可逆、无新数据源。
- **C. 只给「去处理」链接 + 已算好的金额**。人还得自己换算目标值，等于没补上判断。

**最终选择 B**。补充口径：

- 默认与超时都落在「维持目标」，Agent 永远不会借超时替人下调；维持只记「缺口由人接受」，不改任何经营参数。
- 同店同月只提醒一次，处理过（含超时收口）不复活，下个周期按新节奏重新评估。
- 旧条目缺少选项时，打开收件箱会按当前节奏补算，避免同一类升级两种形态。

**回看方式**：目标卡与审计日志均有「目标节奏补救」记录；若改判为三选项，只需在 `applyGoalPaceRemedy` 增加一个分支并复用现有护栏弹窗，升级项结构不变。

## 追加决策（同日 · P35.1 治理自巡检）

**争议**：把结算 / 节奏 / 护栏 / 规则 / 超时收尾从「页面挂载」移到「巡检」后，巡检该在什么时候跑？

- **A. 只并入工作台的 60 秒巡检**：改动最小，但人直接进收件箱或其他业务页时仍不会触发，等于把「必须先打开某张卡」换成「必须先打开工作台」，核心命题没真正补上。
- **B. 只做应用进入时的一次性巡检**：任意入口都能触发，但人在系统里停留期间超时不会持续收尾，且工作台的「巡检」与本动作脱节。
- **C. 两者都做**：工作台 60 秒巡检并入同一轮，同时 AppShell 在进入应用时跑一次。
- **D. 引入真正的后台调度**：本地没有后端与持久任务，只能做假定时器，属于伪装「真实调度」，否决。

**最终选择 C**。理由与口径：

- 巡检逻辑只有一个实现（`runGovernanceSweep`），两个触发点复用，幂等；重复调用只产生一次写入，不会重复建条目。
- 只覆盖 `connected` 店铺，与工作台巡检范围同口径；未授权店铺不产生治理动作。
- 巡检只做「结算 / 提升级 / 按人已配置的默认收尾」，不改目标、不改护栏、不改策略；所有改值动作仍在人的选项里。
- 没有新增后端、依赖或页面；前端 demo 调度「关页面即停」的边界不伪装，仍按 P28.3 口径展示。

**回看方式**：进入任意页面后看目标卡的结算行与待办中心条目是否已更新；若将来接入后端调度，只需把 `runGovernanceSweep` 挂到真实调度器，把 `AppShell` 的一次性触发降级为兜底，调用方接口不变。

## 追加决策（同日 · P36.1 护栏升级就地处置）

**争议**：护栏升级要在收件箱里「一次点选完成」，但有三处口径需要定：

1. 「调至建议值」能不能不打开目标卡弹窗，直接在收件箱写护栏？
2. 「确认维持」算不算一次正式决策，能否让体检停止提醒？
3. 人不处理时，超时能不能替人「确认维持」？

**选项**：

- **A. 收件箱只给「确认维持」，改值仍跳目标卡**：最保守，但只补了一半——人想调值仍要跳四步；P32.2 已经算好的建议值在收件箱里无法落地。
- **B. 收件箱给「确认维持 / 调至建议值」两个选项，复用既有写入语义**：改值调用 `saveGoal`，原因自动记为体检依据，前后值与预演影响写进选项说明和审计；确认写独立的「确认护栏」审计；超时默认维持。
- **C. 为收件箱新造一套护栏快捷表单**：会绕开 P28 的「原因必填 + 影响预演 + 单一数据源」，出现第二条护栏写入路径。否决。
- **D. 超时只关闭提醒、不记确认**：下轮巡检会因「仍未确认」再次生成，形成反复打扰；且无法区分「人看过」与「没人看」。否决。

**最终选择 B**。补充口径：

- 预演没有被跳过：`advice.effect`（放开条数、GMV、毛利）在生成升级项时已算好，并写进「调至建议值」的 consequence；人在点之前就能看到结果，审计也保留同一份依据。
- 原因不是编的：改值原因固定为「收件箱采纳 Agent 体检建议：<依据>」，依据来自体检结论（unlock / tighten 等），与目标卡手填原因一样可回溯。
- 确认 = 人的一次立场，不是改值：写「确认护栏」审计，不伪造 from→to；体检以这条审计为「已看过」，拦截计数从确认时刻重新累计。
- 超时确认的执行者是 Agent，不冒充人：只记确认、不改护栏值；确认后若仍高频拦截，会作为新信息再次进待办，人仍可随时在目标卡改值。
- 读不到体检结论（结果已变化）时不硬造结论，只关闭过期提醒，避免把旧建议写进护栏。

**回看方式**：目标卡「护栏变更 / 确认记录」与审计里会出现「确认护栏」条目；收件箱处理记录保留人的选择、前后值与执行者；若要改判为「收件箱只能确认、不能改值」，删除 `override` 选项与 `applyGuardHealthRemedy` 的调值分支即可，确认与超时口径不受影响。


## 追加决策（同日 · P37.1 账户护栏下发）

**争议**：人已经在目标侧做到「账户下一次目标」，护栏要不要也能一次下发？如果能，账户值覆盖已有单店自设值吗？

- **A. 账户护栏覆盖全部店铺**：一次点完最省事，但会抹掉店长按商圈差异做的自设值（例如临街店更低的折扣上限），且没有逐店确认，错了很难发现。否决。
- **B. 只下发「仍是平台模板值」的店铺，已有自设值的店整店跳过**：人只补空白，不推翻已有判断；表格逐店展示「已有自设 · 不覆盖」，要改仍可进单店目标卡。可逆、可追溯、无新数据源。
- **C. 不做下发，只做多店护栏对比**：只是把 O(N) 录入换成 O(N) 抄写，没有补上人的负担。否决。
- **D. 让 Agent 自动决定哪些店用账户值**：护栏是人的职责，Agent 自动套用会让人失去「在哪儿拦下」的位置。否决。

**最终选择 B**。补充口径：

- 账户值优先取人已设定店铺的一致值（显示「取自 N 家」），没有人工设定才退回平台模板值并标注；不编造行业建议。
- 值相同也写一条「确认护栏」审计，不伪造变更；体检的未确认 / 高频拦截在既有同步里自然收口，不新增关闭逻辑。
- 批量写入只改 `constraints`，不动 `periodKey`；划护栏不能被顺带解释成对本月的目标确认。
- 本轮只补写入侧；同一护栏在多店重复生升级仍登记为下一轮候选，不在本轮扩大范围。

**回看方式**：多店铺概览「账户护栏」行 →「统一护栏」弹窗可看到逐店来源与处理方式；审计里按店按护栏出现「变更护栏 / 确认护栏（账户护栏下发）」；若要改判为可覆盖，只需在 `applyAccountGuards` 去掉自设店铺跳过分支，并把弹窗表格改为可勾选，无数据迁移成本。


## 追加决策（同日 · P39.1 收件箱店铺范围）

**争议**：收件箱要不要跟着顶部店铺范围过滤？过滤会不会让人漏掉其他店铺的升级？

- **A. 完全不过滤，只在条目上标店铺**：最安全，但范围控件在收件箱等于失效，人仍要在混排列表里自己筛，等于把判断留给人。否决。
- **B. 过滤其他店铺，静默隐藏**：上下文最干净，但会让人误以为「待办就这些」，升级项被藏起来，风险最大。否决。
- **C. 过滤 + 显式范围条（本店 / 账户级 / 隐藏条数）+ 一键显示全部**：上下文干净，且隐藏量可见、可逆；账户级条目始终可见并标注。选择 C。
- **D. 单店范围下把账户级「全部（N 家店）」收敛为仅本店**：会改变一次表态覆盖范围的语义，等于让人在一个自己没预期的范围内做部分执行；且与「名单是活的」冲突。否决，登记为下一轮候选再议。

**补充口径**：

- 账户级判定：有 `guardAccount` 名单的按名单判可见；无店铺归属的条目视为账户级，任何范围可见。不会因为换店铺范围而漏掉跨店升级。
- 范围只影响展示与计数，不影响写入；批量操作只在当前可见集合内生效，账户级条目的落库仍按名单逐店执行并在文案里写明覆盖店数。
- 范围复位走同一个全局 `setScope('all')`，不新增第二套范围状态；其他页面随之回到全账号，行为可预期。
- 侧边栏徽标保持全账号计数，范围条上的「其他店铺 N 条未显示」负责解释差值，避免同时改两处计数口径。

**回看方式**：`/inbox` 顶栏切单店 → 卡片顶部出现范围条与「显示全部店铺」；条目标签行出现「账户级」；若将来要改判为「不过滤只标注」，删除 `entriesInScope` 过滤分支与范围条即可，其余计数口径仍成立。


## 追加决策（同日 · P40.1 升级的等待时钟）

**争议**：巡检重算升级内容时，等待起点与超时截止要不要跟着刷新？「内容变了 = 新问题」，听起来该重开窗口；但重开意味着超时策略永远等不到人。

- **A. 内容每次重算都重开窗口（现状）**：翻页 / 刷新 / 每 60 秒巡检都归零，倒计时不可信，超时策略事实上失效。否决。
- **B. 只在内容实质变化（金额、店数、建议值）时重开**：需要给每类升级定义「实质变化」并比较签名，规则多、易漏；而且人已经看到的那条提醒会突然变回满额，仍然不可预期。否决。
- **C. 窗口锚定首次登记，只有人主动改超时策略才重算（本轮选择）**：等待时长单调递增，超时策略可按店铺口径真正触发；内容更新只改「问什么」，不改「还剩多久」。
- **D. 干脆取消超时、只保留人工处理**：等于把「人必须处理每一条」写死，违背核心命题。否决。

**补充口径**：

- 同 id 视为同一条升级；新 id（例如护栏条件换了签名、目标换了月份）才是新条目、新窗口。
- `createdAt`、`deadline`、提醒次数、上报 Owner、暂停、指派人与依据都属于登记痕迹，巡检不得清除；否则「已提醒 N 次」标签会闪没、指派通知会被重复推送。
- 人主动改店铺超时策略时，仍按「首次登记时刻 + 新时长」重算，保证页面文案与实际扫描同一口径。
- 本轮只让既有策略第一次真正可触发，不新增任何自动执行路径；到期结论仍是最保守的「维持现状」。

**回看方式**：收件箱决策卡右侧「剩余 … / 已到期」→ 悬停看精确截止时刻；改店铺超时策略后该数字按新时长变化；若将来要改判为「内容变化即重开」，只需在 `upsertEscalation` 去掉 `deadline` 沿用分支，并接受超时策略不再可达。
